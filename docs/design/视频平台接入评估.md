# 视频平台合规取数：调研报告

> 问题：VIGIL 能不能**合规地**从抖音 / B 站等视频平台取数据？
>
> 本文的写作方针与 `多平台接入.md` 一致：**先说不做什么、为什么，再说怎么做**。
> 末尾附**验证台账**，明确区分「我跑通了的」与「我只是查到的」。

---

## 〇、结论先行

| 档 | 结论 | 依据 |
|---|---|---|
| 🟢 **可做** | 取**视频元数据**（标题 / 简介 / 发布时间 / UP 主）——B 站有**未鉴权即可读**的公开接口，实测跑通 | 见 §二 验证台账 |
| 🟡 **有条件可做** | 取**视频内容文本**（字幕 / ASR）——技术上可行，但**合规边界从"读取"移到"内容授权"** | 见 §四 |
| 🔴 **不做** | 逆向签名（wbi / a_bogus）、破解、模拟登录的高频爬取 | 违反用户协议，且有法律与封号风险，与赛题第⑧条观感冲突 |

**最要紧的一句话**：视频平台这条路，**卡点从来不是"技术能不能取"，而是"取来的东西和 VIGIL 要的东西不是一回事"**。
VIGIL 的管线是为「短文本 → 结构化条目」造的；视频是「长音视频 → ？」，中间缺一整条独立管线。

---

## 一、先说清楚：赛道判定

本报告是**在 `多平台接入.md` 已有结论之上的复核**。那份文档当时把视频追踪列为：

> ⚪ **不纳入本轮**。它需要一条独立管线（转写 → 分段 → 抽取），不是加个 Source 就完事。

**这个判断依然成立**，但理由需要补一条更硬的：§四 会说明，**接进来之后会撞上 `content` 字段的文本契约**。

## 二、验证台账（我实际跑通的）

以下均为**本机实测**（2026-10-16，中国区网络，无任何登录态 / cookie）：

| 目标 | 方式 | 结果 |
|---|---|---|
| B 站视频详情 | `GET https://api.bilibili.com/x/web-interface/view?bvid=BV1GJ411x7h7` | ✅ `code: 0`，返回完整 JSON（`title` / `desc` / `pubdate` / `owner` / `cid` / `stat`） |
| B 站播放器信息 | `GET https://api.bilibili.com/x/player/v2?bvid=...&cid=...` | ⚠️ `code: 0`，但 **`subtitle.subtitles` 为空数组**，且 `login_mid: 0`（未登录） |
| B 站开放平台 | `https://open.bilibili.com/` 与 `/doc` | ✅ HTTP 200 |
| 抖音开放平台 | `https://developer.open-douyin.com/` 及文档页 | ✅ HTTP 200 |
| 快手开放平台 | `https://open.kuaishou.com/` | ✅ HTTP 200 |

⚠️ **关于 B 站字幕那条，必须诚实标注**：我拿到的是**空数组**，但我**无法区分**这是
「该视频本来就没有字幕」还是「未登录所以不下发」。这两个原因在本机无法证伪。
所以正确记法是：**未登录态下取不到字幕**，而不是「B 站字幕必须登录」。

**没验证到的**：抖音 / 快手 / 小红书的具体数据接口签名要求、各开放平台的资质门槛、
第三方数据服务（新榜 / 飞瓜）的报价。这些在 §六 列为待核实项，**本文不对它们下结论**。

## 三、各平台的真实状况

### 🟢 B 站 —— 唯一"读得到且无争议"的

| 项 | 说明 |
|---|---|
| 合规基础 | 有正式的**开放平台**（`open.bilibili.com`），也存在**未鉴权即可读**的公开 web 接口 |
| 能取什么 | 视频元数据：标题、简介、发布时间、UP 主、播放/点赞数 |
| 关键风险 | 公开 web 接口**不是承诺的 API**——B 站有权随时加风控（wbi 签名、`a_bogus`）。**这决定了它不能作为产品的唯一依赖** |
| 信号密度 | **低**。`多平台接入.md` 的判断继续成立：「UP 主更新了」与「我该做什么」之间隔着一层 |

**为什么仍然值得单列**：如果某个学院 / 社团**真的用 B 站发通知**（确实存在这种用法），
那这个源的信号密度会从"低"跳到"高"。**但那是一个具体用例，得先找到这个用例再写代码**，
而不是先写通用 B 站追踪器。

### 🟡 抖音 / 快手 —— 开放平台存在，但"能拿数据"和"能拿到我们想要的"是两回事

两家的开放平台（`open.douyin.com` / `open.kuaishou.com`）站点均可达，但**要注意它们的定位**：

- 这类平台主要服务**内容发布方**（让 UP 主能发视频、做账号管理）与**服务商 / 广告主**，
  而不是让第三方**追踪任意账号的更新**。
- 「行业数据 / 内容数据」类能力通常**走商务合作或服务商资质**，个人开发者基本拿不到。

⚠️ **这一条我未在本次调研中完成验证**（各平台资质矩阵页未能逐项读取）。
**在材料或代码里引用之前必须先核实**——不要把一个"理论上开放"说成"我们能申请到"。
这正是 `contest-docs-lag-source-paths` 那条教训的适用范围：**结论性事实也会错，硬事实须查原件**。

### 🔴 小红书 —— 开放平台面向电商 / 服务商

内容数据能力是否对外开放**未验证**。小红书开放平台的历史定位是电商与服务商接入，
不面向"追踪内容更新"这类需求。**在核实前按"不可得"处理。**

### 🔴 明确不做

| 方案 | 为什么 |
|---|---|
| 逆向 wbi / `a_bogus` 签名 | 违反用户协议；签名算法随时变，**产品会周期性地烂掉** |
| 破解 App / hook 客户端 | 封号风险 + 法律风险，与赛题第⑧条观感冲突 |
| 模拟登录后高频抓取 | 同上，且**违反《数据安全法》相关口径** |

⚠️ **「不做」要在材料里主动说**——它展示的是判断力，不是能力缺失（同 `多平台接入.md` 的方针）。

## 四、⚠️ 真正的架构阻碍：撞上 `content` 的文本契约

这一节是本报告**最重要的部分**。即使 §三是全部绿灯，接进来仍然会撞墙。

### 撞的第一堵墙：`SourceMessage.content` 必须是文本

`vigil/source.py:41` 的契约写得很硬：

```python
@dataclass(frozen=True)
class SourceMessage:
    """``content`` 必须是**已抽成文本**的正文（不是 BLOB）"""
    content: str
```

而 `ingest.py:43` 的 `messages.content` 列是 `TEXT NOT NULL`。

**推论**：视频源**不能**直接接。要接，源实现里必须先把「视频」变成「一段文本」——
也就是**转写必须发生在源内部**（或源之前），不能推给下游。

### 撞的第二堵墙：prefilter 是给聊天消息调的

`vigil/prefilter.py` 的全部判据都隐含「这是一条短消息」：

| 判据 | 行号 | 对视频的后果 |
|---|---|---|
| `MIN_BYTES = 4`（按**字节**算） | `prefilter.py:23` | 无害，视频转写必然超长 |
| `DEFAULT_KEYWORDS`（通知 / 报名 / 截止…） | `prefilter.py:27` | ⚠️ **关键词是为群通知选的**，一份 20 分钟视频的转写稿几乎必然命中若干，等于筛子失效 |
| `BARE_ACK`（全匹配才丢） | `prefilter.py:44` | 无害 |
| `_flood_ids`（同群同一人 60 秒内 3 条相同） | `prefilter.py:90` | 无害 |

**真正的后果**：视频转写的文本**太长**，会直接撑爆 `make_batches`（`prefilter.py:240`，`max_batch=30`）
与下游的 LLM 上下文。**长期音视频需要先分段，再走逐段抽取** —— 这就是
`多平台接入.md` 说的「一条独立管线」，不是加个 `Source` 就完事。

### 撞的第三堵墙（合规侧）：授权边界从"读取"移到"内容"

`docs/design/隐私边界.md` 把 VIGIL 的风险论证建立在两件事上：

> | **读取**（本机 QQ 库） | 读自己的数据，法理上最轻 | 保留 |
> | **传输**（发给云端 LLM） | 「向第三方提供个人信息」 | **移除** |

**视频场景下这个论证不成立**：视频的著作权属于 UP 主，**下载视频 / 音频做 ASR 是复制行为**，
不是"读自己的数据"。

**合规边界重构**：

| 场景 | 判定 |
|---|---|
| ✅ **自己上传 / 已获授权**的内容做 ASR | 边界清晰，推荐 |
| 🟡 平台**自带字幕**直接取（不下载音视频） | 比 ASR 干净得多——**没有复制音视频** |
| 🔴 下载他人视频做 ASR | 涉及复制权 / 信息网络传播权，需要另行论证 |

⚠️ **这条直接决定了推荐路线**：**优先取字幕，而不是优先做 ASR。**
因为取字幕**不复制音视频**，合规论证短得多。而 B 站字幕未登录取不到（§二），
所以**授权路线应该是"官方接口 / 已授权内容"**，而不是"想办法绕过去拿字幕"。

## 五、推荐路线（如果要做）

**按此顺序，且每一步都要能独立收尾**：

| 序 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| 0 | **先找到一个真实用例**：某个学院 / 社团真的在用视频平台发通知 | 找不到就不要做。信号密度低的源会稀释产品价值 |
| 1 | 只取**元数据**（标题 / 简介 / 发布时间），落成一条 `SourceMessage` | 元数据就是**短文本**（§四第一堵墙绕过）；`content` 用「标题 + 简介」拼接，天然满足契约 |
| 2 | 验证双源并存（RSS 源 + 视频源同跑） | 这正是 `多平台接入.md` 建议的实施顺序第 2 步，**`Source` seam 至今没验过并存** |
| 3 | 视时间决定是否做转写 | 只有第 1、2 步都稳了、且用例真实存在时才做 |

⚠️ **第 1 步是本文最有价值的具体建议**：**取元数据不需要 ASR，也不需要字幕，
不需要下载任何音视频**——标题/简介本身就是文本，直接能满足 `content: str` 契约。
**这可能是视频平台唯一"低成本 + 无争议 + 立刻能演示"的接入点。**
