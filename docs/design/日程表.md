# 日程表：从「信息聚合」到「时间分配」

> 方向：在现有 `Calendar` 视图上做增强，**不新建模块**。
>
> 本文档记录现状、缺口、以及每一步**复用什么已有设施**。
> 凡是标 ⚠️ 的地方，都是「不这么做会出问题」的实测或结构性理由。

---

## 一、现状：日历已经是「只读散点」

`/api/calendar`（`vigil/api.py:1093`）已经能返回带死线的条目，前端
`web/src/views/Calendar.tsx`（291 行）按月渲染成一个 6×7 网格。

**它现在能做的**：把有 `deadline_ts` 的条目按日子摆到日历格子里。

**它做不到的三件事**（也就是这次要补的）：

| 缺口 | 用户的真实处境 |
|---|---|
| **没有状态** | 看过了、办完了、不打算办 —— 界面上**长得一样**。日历越用越满，而"还没办的"淹没在"早就办完的"里 |
| **没有优先级** | 同一天 5 条通知平铺，看不出哪个**今天必须动** |
| **没有临近提醒** | 死线是静态的：今天和三天后**颜色一样**。而"截止日期"的信息价值随日子逼近而上升 |

⚠️ 第三条是这个功能真正的价值所在 —— 也是 VIGIL 那句话
（「漏掉一条可能是几万块的奖学金」）在产品上的落点。

---

## 二、复用：**不新建数据模型**

「已办 / 忽略」需要**状态**。直觉上要加一张 `todo_status` 表 —— **不要**。

`vigil/overrides.py` 已经有**人工干预层**，而且它天生就是干这个的：

| 已有设施 | 位置 | 为什么它合适 |
|---|---|---|
| `item_edits` append-only 事件表 | `overrides.py:47` | 「已办」就是一条事件，天然可撤销、可审计 |
| `ACTION_SET_FIELD = "set_field"` | `overrides.py:38` | **现成的动作类型**，`field="done"` 即可 |
| `item_state` 物化视图 | `overrides.py:47` | 读路径 JOIN 它，不必每次折叠事件流 |
| 撤销（`/api/undo`） | `api.py:1210` | 点错了能撤 —— **不需要为新状态重写** |

**所以「已办」的实现是**：

```
写：POST /api/items/{id}/field  {"field": "done", "value": "1"}
    → overrides.set_field(...)        ← 复用现有写路径
读：item_out() 里带上 done 字段        ← 复用现有物化视图
撤：POST /api/undo                    ← 完全不动
```

⚠️ **为什么不用新表**：`overrides.py:883` 写过一条教训 ——

> `SELECT deleted FROM item_state` 是**第二份实现** —— 它一定会漂移。

新增一张状态表意味着「这个 item 算不算办完」要在**两处**判断（新表 + 现有
overlay 的软删/改类目），而两处迟早漂移。**沿用同一个事件流是唯一不会漂移的做法。**

## 三、三个阶段（每阶段都能独立演示）

### 阶段 1：状态标记（最小可用）

**改动面**：`api.py` 加一个写端点 + `item_out()` 多一个字段 + `Calendar.tsx` 加个勾选框。

```
✓ 已办     → 变灰、沉到底部
✗ 忽略     → 隐藏（可开关）
（无标记） → 正常
```

**出口判据**：标记「已办」→ 刷新页面 → 状态还在；`/api/undo` 能撤回。

⚠️ **必须走 overlay**：主库 `mode=ro`，
`api.py:222` 的 `db_uri` 与 `connect()` 的 docstring 明写「**绝不**在此调 `store.ensure_schema`」——
它是只读连接，写操作会被 SQLite 直接拒绝。状态只能进 overlay。

### 阶段 2：按天分组 + 优先级排序

现在 `deadlines_in_range`（`store.py:1116`）按 `(deadline_ts, event_ts, item_id)` 升序。
**保持这个顺序**，前端按 `deadline_ts` 的日期切组即可。

**组内排序依据**（三条，都是现成字段）：

1. **未办 > 已办**（状态来自阶段 1）
2. **同类目内的死线更近者优先**（`deadline_ts` 升序）
3. **高置信度优先**（`items.confidence`）—— ⚠️ 这条要谨慎：
   实测这批数据里 `confidence` 只有 `0.9` 与 `0.0` 两档（8B 不给这个字段时
   回落到 0.0，见 `refine.py:339`）。**用它当排序键等于按"模型有没有给置信度"排**，
   语义很弱。**建议先不用它**，等有真实分布再说。

### 阶段 3：临近提醒（**这是价值最高的一步**）

**分级**（用现成的 `deadline_ts` 与当前时间算，不引入新字段）：

| 距今天数 | 视觉 | 理由 |
|---|---|---|
| 今天 / 明天 | 🔴 置顶 + 加粗 | 还来得及做 |
| 2–3 天 | 🟠 正常显示 | 该规划了 |
| 4–7 天 | ⚪ 正常 | 知道就行 |
| > 7 天 | ⚪ 折叠 | 噪声 |
| **已过期** | ⬜ 划掉 | ⚠️ **不要隐藏** —— 「我漏了什么」本身是信息 |

⚠️ 最后一条是刻意的：这个产品的存在理由就是**怕漏**。
把过期项藏起来，等于把"你漏了"这件事也藏起来。

## 四、⚠️ 这一版**不做**的（以及为什么）

| 不做 | 理由 |
|---|---|
| **自动排期**（"这条通知该插在哪节课之间"） | 需要「我的课表」这个约束源 —— 见 `日程表-课表约束.md`（规划中）。没有课表就没有排期依据，硬做只能猜 |
| **冲突检测** | 同上 |
| **推送/通知** | 代码里**完全没有**推送能力（已核实）。这是独立功能，见 `推送.md`（规划中） |
| **重复日程**（每周的课） | 需要 recurrence 规则（RRULE 或简化版）。当前 items 是「一次性的通知」，不是日程 |

---

## 五、为什么「不做课表」也是对的

我原本想直接把课表做进来，但盘了一下发现它是**另一个量级**的东西：

| | 日历增强（本文档） | 课表约束源 |
|---|---|---|
| 新数据模型 | ❌ 不需要（复用 overlay） | ✅ 需要（课表 + 排期结果） |
| 新视图 | ❌ 改现有 | ✅ 可能要新页面 |
| 新 API | ❌ 一个写端点 | ✅ 一组 |
| 核心算法 | ❌ 排序 | ✅ 冲突检测 / 空闲块推荐 |

**先做增强能立刻演示，而课表是它的前提而非替代。** 分两步走，
第一步的产物（带状态、带优先级的日程）第二步直接复用。
