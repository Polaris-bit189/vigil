# 时间安排：分钟级日程

> 目标：把条目排成**具体到分钟**的一天。行程时间取**地图软件返回的数据**，
> 出行方式（步行/骑行/公交/驾车）**由用户设置**，不写死。
>
> ⚠️ 本文档分两部分：
> **§一–§四 是已核实的**（每条都标了代码位置，可直接动工）；
> **§五 是待定区**——那里每一项都写明**卡在哪**，而不是含糊带过。

---

## 一、已核实的事实（决定了能做什么）

| 事实 | 值 | 位置 |
|---|---|---|
| 条目已有「死线」 | ✅ `deadline_ts`，但**只到日** | `refine.py:235` 用 `%Y-%m-%d` 解析 |
| 条目已有「事件时间」 | ⚠️ 是**消息发出时间**，不是活动时间 | `refine.py:367` `event_ts=source.ts` |
| 条目的提示词要求 | 只抽 `deadline`/`place`/`amount`/`confidence` | `refine.py:106-108` |
| **合成语料里的时刻** | ❌ **一个都没有**（全是「9月30日」这种日期级） | 实测 grep `demo/corpus.toml` 零命中 |
| 地点字段 | ✅ `place`，实测覆盖 **32%**（120/375） | 见 `地点导航.md` |

### 由此得出的**硬结论**

> **现在做不了分钟级安排。** 因为数据里**没有"活动几点开始"这个信息** ——
> `deadline_ts` 只到日，`event_ts` 是消息时间。
>
> 这不是缺算法，是**缺输入**。任何"排期算法"在没有活动时刻时都只能凭空发明一个。

## 二、必须补的第一步：`start_ts`（活动开始时刻）

### 改什么

**提示词**（`refine.py:106-108`）加一个字段：

```json
{"deadline": "YYYY-MM-DD 或 null",
 "start": "YYYY-MM-DD HH:MM 或 null",   ← 新增
 "place": "..."}
```

**解析器**（`_parse_deadline`，`refine.py:219`）扩成**两个**：

| 函数 | 格式 | 用途 |
|---|---|---|
| `_parse_deadline` | `%Y-%m-%d` | 保持不动（死线只到日，这是对的） |
| `_parse_start`（新） | `%Y-%m-%d %H:%M` | 活动开始，到分钟 |

⚠️ **不要合并成一个函数**：死线**本来就只到日**（「9月30日前完成」），
强制它带时刻会让模型编一个时间出来。两个字段的**精度要求不同**，
共用一个解析器迟早会把其中一边的语义弄坏。

### ⚠️ 连带改动（别漏）

| 项 | 为什么 |
|---|---|
| **`PROMPT_VERSION` 升版**（`refine.py:37`） | 提示词变了，产出与前版不可比。不升版会让 `refine_runs` 里两版混在一起 |
| **合成语料加带时刻的模板** | 现在是零样本，**改完也测不了**。要加「周三 14:00 在体育馆」这类模板 |
| **`deadline.py` 的正则** | 它只认日期。`start` 的**字面依据**校验需要新正则（见下） |

### ⚠️ `start` 也要过机器闸门

`deadline_supported`（`deadline.py:65`）的判据是「这个日期能否在源文里**逐字找到**」。
**`start` 必须过同一道闸** —— 否则模型会给「明早集合」编一个「08:00」。

新正则要认这些写法（和日期同族，但带时刻）：
```
14:00        14点        下午2点        晚上7点半
2026-09-16 14:00        9月16日下午2点
```

## 三、行走时间：取地图 API

### 已定的做法

**不自己算距离**，调用地图服务商的**路径规划 API**。

```
起点：上一条日程的地点
终点：本条日程的地点
出行方式：**用户自己设**（步行 / 骑行 / 公交 / 驾车）
↓
华为云 KooMap 路径规划 API
↓
返回：距离（米）+ 预计耗时（分钟）
```

⚠️ **出行方式不写死步行。** 理由：校园里有人骑车、有人坐校巴，
而「走 15 分钟」与「骑 5 分钟」对出发时刻的影响是**分钟级**的 ——
猜错这个，整条时间线就偏了。做成用户设置项（存 localStorage 或后端），
默认值可以给「步行」。

⚠️ 好在 KooMap 的路径规划 API **本来就支持五种出行方式**（见 §待定 2 的证据），
所以这不是"额外要求"，是**用它本来就有的参数**。

### ⚠️ 三个必须先解决的问题

**① 需要坐标，而 `place` 是纯文本。**

路径规划 API 要的是 `(经度, 纬度)`，不是「食堂二楼」。
所以要先走**地理编码**（geocode）：文本 → 坐标。

⚠️ 而**校园内部建筑在公开地图上没有独立点位**（见 `地点导航.md` §二）——
「食堂二楼」geocode 出来会是学校大门的坐标。
**这意味着"从宿舍到食堂"的距离会被算成"到校门"的距离。**

**处置**：见 §五 待定区第 1 项。

**② 需要开通地图服务（华为云 KooMap）。**

需在控制台开通并拿 Key，有免费额度但要实名 —— 与其他华为云服务同一套流程。
✅ **好消息：它是华为云自己的服务**，所以这一项**顺带满足赛题**
「关联开通华为云服务」的要求，不是纯粹的成本。见 §五 待定 2。

**③ 每条都调 API 会让打开页面变慢。**

一条日程算一次行程时间，一屏 20 条就是 20 次 API 调用。
**必须缓存**：`(起点, 终点)` 相同的查询结果缓存（Redis 已在架构里，见 `云端部署.md`）。

## 四、已知可行的部分（可以先动工）

即使 `start_ts` 还没做，**下面这些现在就能做**：

| 做什么 | 依赖 | 成本 |
|---|---|---|
| **死线倒计时**（今天/明天/还有 N 天） | 只需当前时间 | 低 —— 见 `时间注入.md` |
| **地点 → 地图搜索链接** | 只需 `place` | 低 —— 见 `地点导航.md` |
| **补 `start_ts` 到抽取管线** | 提示词 + 解析 + 语料 | 中 |
| **日程列表按时刻排序** | 要 `start_ts` | 低（在上一项之后） |
| **行走时间** | 要 `start_ts` + 坐标 + API Key | 高（见 §五） |

**建议顺序**：倒计时 → 地图链接 → `start_ts` → 排序 → 行走时间。
每一步都能单独演示，且**前一步是后一步的前提**。

## 五、⚠️ 待定区（每一项都写明卡在哪）

> 这里放**现在定不了**的事。它们不是"以后再说"，而是**有具体阻塞项**，
> 需要先解决那个阻塞才能定。

### 待定 1：校园内部地点没有坐标，怎么算行走时间？

**卡在**：`place` 是「食堂二楼」这样的文本，而地图 API 要坐标；
且校园建筑在公开地图无独立点位。

**三个候选做法，都还没验证**：

| 做法 | 说明 | 需要验证什么 |
|---|---|---|
| A. 接受"到校门"的精度 | 直接用 geocode 结果的坐标 | ⚠️ 「从宿舍到食堂」会算成「到校门」，**误差可能是几倍** |
| B. 用户自己标点 | 让用户在设置页给常用地点打一次坐标 | 需要设计 UI；但**一次标注长期可用** |
| C. 用户填固定耗时 | 「宿舍→教学楼 10 分钟」 | 最简单，但**退化成手填**，失去了"自动"的价值 |

**为什么现在定不了**：三条都可行，但**A 的误差有多大**需要真实数据才能判断
（我手上只有合成语料里的编造地点，测不出）。

### 待定 2：用华为云的还是第三方？

**已核实（2026-10-14）**：**华为云有地图与路径规划能力。**

| 项 | 证据 |
|---|---|
| 服务名 | **KooMap 云地图服务**（开天 aPaaS 下）—— `huaweicloud.com/product/koomap.html` 实测可访问 |
| 路径规划 | 华为云社区文章明载：*「介绍地图路径规划API，支持**驾车**、**步行**、公交、骑行及电动车五种出行方式」* |
| 结论 | **做得到，且能用华为生态** —— 不必引第三方 |

⚠️ **仍需去控制台确认**（本文档不硬编码，避免过期误导）：

| 待确认 | 怎么确认 |
|---|---|
| 属 KooMap 还是 MapDS | 控制台搜「地图」看入口 |
| **是否返回耗时**（而不只是画路线） | 查 API 文档返回字段有无 `duration` / `distance` |
| 计费与免费额度 | 控制台价格页 |
| ⚠️ 校园内部坐标精度 | 与 §待定 1 同一个问题，**不因换厂商而消失** |

**为什么这条重要**：赛题要求体现华为云产品价值。**用 KooMap 而不是高德，
让"技术栈复合度"多一项** —— 而这是往届差距里**唯一可补的那一项**。

### 待定 3：行走时间的"出发提醒"

有了耗时之后，"该几点出发"是水到渠成的：
`活动开始时刻 - 行走耗时 = 出发时刻`。

**但有个未定**：要不要**提前几分钟**（找座位、等电梯）？
这个缓冲值**因人因地而异**，写死一个数字（比如 5 分钟）是**替用户做了个他不一定认同的决定**。

**候选**：做成用户设置项。⚠️ 但这又增加一个"个人参数"——
而本项目已经因为"课表"这个个人参数把排期功能推到了第二阶段（见 `消息整合与排期.md`）。

### 待定 4：这条路要不要做？

**卡在**：这是个**产品定位决定**，不是技术决定。

```
现状定位：聚合群消息 → 告诉你"有什么"
加入排期：个人日程助理 → 告诉你"什么时候做什么"
```

⚠️ 后面这个定位**更重**（要用户提供课表、地点标注、时间偏好），
但也**更有价值**（从"信息工具"变成"时间管理器"）。

**这个决定必须你来做** —— 它决定了是否值得投入 §二–§三 的全部工作量。

## 六、一句话总结

> **已定**：
> · 补 `start_ts`（活动开始时刻）是前提 —— 现在数据里完全没有
> · 行走时间**不自己算**，取地图 API
> · 出行方式**用户自己设**（步行/骑行/公交/驾车），不写死步行
> · 地图用**华为云 KooMap**（已核实它有路径规划，支持五种出行方式）
>
> **待定**（都写明了卡在哪，见 §五）：
> · 校园内部地点的坐标精度 —— 4 个候选做法，**误差有多大需要真实数据**
> · KooMap 是否返回**耗时**字段（不只是画路线）—— **需控制台确认**
> · 出发提醒的提前量要不要做成设置项
> · **以及这条路整体要不要走**（产品定位决定，得你拍板）
