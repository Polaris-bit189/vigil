# 多平台接入：架构接口与风险分级

> 方向：**写架构接口 + 如实分级每个平台的风险**。不碰需要逆向或封号风险的方案。
>
> ⚠️ 本文档的方针是**先说不做什么、为什么**，再说怎么做。
> 一个只列"支持哪些平台"的文档是营销，不是工程设计。

---

## 一、好消息：接口**已经留好了**

这次重构（见 `数据源适配层.md`）建的 `Source` 协议，**本来就是为多源留的口子**：

```python
class Source(Protocol):
    def list_groups(self) -> list[tuple[int, int, int]]: ...
    def group_names(self) -> dict[str, str]: ...
    def read_group(self, gid: int) -> GroupRead: ...
    def sender_names(self) -> dict[tuple[int, str], Sender]: ...
    def media_index(self) -> dict[str, pathlib.Path]: ...
```

**接入一个新平台 = 实现这五个方法**（`vigil/source.py:94`），然后在
`open_source()`（`source.py:131`）加一个分支。

**下游一行都不用改** —— 因为下游（`store` / `reader` / `digest` / `api`）
只认三张派生表的形状，不认数据来自哪。

⚠️ 这是**已经验证过**的，不是设想：这次重构正是用同一个机制把
「QQ 加密库」换成了「合成语料」，而下游 847 个测试**一个都没改**。

## 二、各平台的真实状况（如实分级）

### 🟢 可行：网页 RSS / 校园通知页

| 项 | 说明 |
|---|---|
| 接口 | HTTP + HTML 解析，或无鉴权的 RSS/Atom |
| 合规 | **无争议** —— 公开信息 |
| 信号密度 | **高**（教务处/学工处的通知页正是这个产品的目标场景） |
| 实现成本 | 低（一个 `requests` + 可选 `feedparser`） |
| 风险 | 站点改版会破坏选择器 → **必须配解析失败的告警**，不能静默返回空 |

⚠️ **这一项应当排第一** —— 它合规、信号密度最高、且**不依赖任何逆向**。

### 🟡 可行但信号弱：B 站 / 有公开 API 的平台

| 项 | 说明 |
|---|---|
| 接口 | B 站有公开 API（UP 主动态、视频更新） |
| 合规 | 公开内容，无争议 |
| 信号密度 | **低** —— "UP 主更新了"与"我该做什么"之间隔着一层 |
| 实现成本 | 中 |
| 真实价值 | 除非**特定 UP 主发的是校园通知**（有些社团/学院就这么发），否则噪声大于信号 |

### 🔴 不做：微信（2026-10-16 已核实排除，不再列为候选）

微信**不再作为候选数据源**。三条路都查到底了：

| 路径 | 核实结论 |
|---|---|
| 个人号官方 Bot | 微信 2026-03 上线 ClawBot / iLink 官方通道（`github.com/Tencent/openclaw-weixin`、npm `@tencent-weixin/openclaw-weixin`），但**仅支持单聊**：源码 `policy: { groupPolicy: "disabled" }`；协议文档声明「类型里有某字段 ≠ 插件支持该功能」；CHANGELOG 全篇未提群聊。**群聊取数不成立。** |
| 企业微信「会话内容存档」 | 官方合规 API，**确实覆盖客户群（外部群）**；但需**企业认证主体 + 按存档人数付费 + 员工/客户知情同意**（外部联系人默认同意、可主动拒绝）。校园群场景三条均不成立。 |
| 逆向 hook 客户端 | 封号风险明确，且违反服务条款。 |

⚠️ 「不做」这件事**要在材料里主动说** —— 它展示的是判断力，不是能力缺失。

### 🔴 不做：微博

| 项 | 说明 |
|---|---|
| 接口 | 有 API，但需申请且个人号额度极低 |
| 信号密度 | **极低** —— 微博的信息形态与"我该做什么"几乎无关 |
| 结论 | 不做。**列出来是为了说明"我们评估过"** |

### ⚪ 视频追踪（抖音 / B站视频内容）

| 项 | 说明 |
|---|---|
| 技术可行性 | 需 ASR（语音转文字）+ 摘要，链路长 |
| 与现有架构的关系 | **不匹配** —— 现有管线是「短文本 → 结构化条目」，而视频是「长音视频 → ？」 |
| 结论 | **不纳入本轮**。它需要一条独立管线（转写 → 分段 → 抽取），不是加个 Source 就完事 |

## 三、⚠️ 一个必须说清的架构限制

`Source` 协议的方法名**带着「群」的语义**（`list_groups` / `read_group`）。

对 RSS 这类源，一个"群"就是**一个订阅源** —— 语义能对上（都是"一个有名字的消息容器"）。
但**别被名字骗了去改下游**：`group_id` 在下游是 `INTEGER`，而 RSS 源的自然标识是 URL。

**做法**：在源实现里**给每个源分配一个稳定的整数 ID**（如按 URL 哈希取正数），
`group_names()` 返回 `{str(id): "源名称"}`。这样下游完全不用改。

⚠️ 这正是「归一化由源负责」那条原则的又一次应用 —— 见 `数据源适配层.md` §二。
**源专注"怎么取"，ingest 专注"怎么落"。**

## 四、建议的实施顺序

| 序 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| 1 | **网页 RSS / 校园通知页** | 合规、信号密度最高、成本最低。**且能立刻演示**（拿本校教务处页面试） |
| 2 | **同一份代码跑双源** | 验证 `Source` seam 真的成立（现在是"一源一实现"，没验过并存） |
| 3 | 视时间决定 B 站 | 有真实用例才做（某个学院真在 B 站发通知） |
| — | 微信 / 微博 | **不做**，在材料里说明理由（微信三条路均已查实，见 §二） |

## 五、这一项对材料的价值

**初赛材料有一栏 1000 字是「华为云产品使用价值」**，与这里没直接关系。
但**「创新性」那 60% 有**：

> 「**从单一数据源到多源聚合的架构可扩展性**」

这个叙述的好处是**它已经成立**（不是画饼）—— 这次重构就是证明：
换数据源而下游零改动。评委可以自己 `git clone` 跑一遍看。

⚠️ 但**别把没做的平台写进材料当作已实现**。组委会会复现
（赛题第⑦条：复现不符即取消资格）。**写"已实现 RSS 源 + 架构可扩展"，
而不是"支持微信微博 B 站"。**
