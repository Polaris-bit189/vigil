# 数据源适配层

> 为什么换数据源**不需要改下游**，以及那条 seam 在哪。

---

## 一、问题

VIGIL 的原始数据源是**本机 QQ 加密库**。它有两个麻烦：

1. **不可复现** —— 评委没有那个库，`git clone` 之后跑不起来
2. **不可分发** —— 读它需要解密逻辑，而那份代码不该进公开仓库

而下游（`store` / `reader` / `digest` / `api`）**只关心结构化结果**，
不关心那些结果从哪来。

---

## 二、解法：把「怎么取」与「怎么落」分开

```
        ┌─────────────────┐
        │  Source 协议     │  ← 「怎么取」：QQ 源 / 合成源 / 未来的任何源
        └────────┬────────┘
                 │ SourceMessage（归一化）
                 ▼
        ┌─────────────────┐
        │  ingest.py       │  ← 「怎么落」：写三张派生表
        └────────┬────────┘
                 │
                 ▼
   messages / sender_names / msg_media   ← **下游唯一契约**
                 │
                 ▼
   store / reader / digest / api         ← 一行都不用改
```

**支点是三张派生表的 schema，不是代码。** 只要源产出同样形状的数据，
下游完全无感 —— 这是整个重构能成立的原因。

### 为什么让源返回归一化的 `SourceMessage`

早年的 `export.py` 从 QQ 库读原始行（38 列纯数字列名），然后在编排层
里写 `row[17]`、`text.readable(...)`、`media.refs(...)`。
那三件知识（列索引 / protobuf 解析 / 图片名正则）**全是 QQ 专有的** ——
把它们放在编排层，换源时就得连编排层一起改。

归一化之后：**源专注"怎么取"，ingest 专注"怎么落"**。
代价是源实现多做一点转换 —— 但那本来就是它该做的。

## 三、`Source` 协议的五个方法

```python
class Source(Protocol):
    def list_groups(self) -> list[tuple[int, int, int]]: ...
    def group_names(self) -> dict[str, str]: ...
    def read_group(self, gid: int) -> GroupRead: ...
    def sender_names(self) -> dict[tuple[int, str], Sender]: ...
    def media_index(self) -> dict[str, pathlib.Path]: ...
```

方法集**刻意与 ingest 的四个取数动作一一对应** —— 少一个都落不出三张表。

用 `Protocol` 而不是抽象基类：私有 QQ 源无需改动即可接入，
而两个实现（`SyntheticSource` / `QQSource`）就够，不做注册表（YAGNI）。

### ⚠️ 一条硬契约：`read_group` 读不到必须抛

```python
def read_group(self, gid: int) -> GroupRead:
    """⚠️ **读不到必须抛异常**，不许返回空的 GroupRead ——
    空返回值与"这个群本来就没消息"**完全同形**，调用方会把整群读不到
    记成 0 条成功，于是日报会以"这天很安静"的口气叙述一个整个群没读进来的日子。
    """
```

这条不是理论：早年 QQ 源里有一段"读不到就 `return GroupRead([], [])`"，
实测导致**整群读不到时退出码仍是 0**，而日报照写。测试里有一对用例守着
（抛 ⇒ 退 1；不抛 ⇒ 退 0，两个不同的群各一个）。

## 四、合成语料：**是数据，不是代码**

`demo/corpus.toml` 是语料规格 —— 群、发信人、消息模板、噪声模板。
改语料**不用改生成器**，而它可读、可 diff、可评审。

```toml
[[templates]]
kind = "notice"
deadline = "literal"        # ← 这条的截止日在正文里有字面依据
text = "关于{term}的通知：请于{date_cn}前完成，逾期不再受理。"

[[templates]]
kind = "academic"
deadline = "implied"        # ← 只给相对说法（「下周」）⇒ **应被闸拦下**
text = "老师说这门课下周收作业，大家抓紧。"
```

`deadline` 那一列是刻意的：**只测"能过闸"的语料，等于没测闸门**。
两类都要有。

### 确定性是设计约束

同一个 seed 必须产出**逐字节相同**的库 —— 否则「复现」说不通
（评委跑出来的与材料里的不是一个东西）。

两处踩过的坑：

1. **不能用内建 `hash()`** —— 它对字符串加了**每进程随机**的盐
   （`PYTHONHASHSEED`），实测"同一个 seed 两次跑出不同的 `uin`"。
   改用 md5 取前 8 位。
2. **不能用 WAL** —— WAL 下新数据先进 `-wal` 侧车，主库内容取决于事务边界。
   `ingest` 用 `journal_mode = DELETE`。代价是并发写会锁 ——
   但写路径本来就上了 `SingleInstance` 文件锁，那问题在这里不存在。

## 五、两条产出路径

| 路径 | 用途 |
|---|---|
| `SyntheticSource → ingest()` | **测试用**：证明 seam 接得上（走完整编排） |
| `write_corpus() → demo/vigil-demo.db` | **演示用**：评委 clone 下来就有数据，不必跑生成器 |

两条产出同一形状的库，所以前者能验证后者。

---

## 六、加一个新源要做什么

1. 实现 `Source` 的五个方法
2. 在 `source.open_source()` 里加一个分支
3. 在 `config/groups.toml` 的 `source` 键写它的名字

**下游一行都不用改。** 如果发现要改下游，说明源的实现漏了归一化 ——
那是源的责任，不是下游的。
