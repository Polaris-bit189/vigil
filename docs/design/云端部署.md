## 二、为什么本地仍用 SQLite

赛题任务第 2 条要求的是**「关联 RDS、REDIS 等华为云服务的快速开通创建」**
—— 考的是**开通创建这个动作**，不是"把应用迁到 MySQL 上运行"。

所以本方案：
- **本地**：仍用 SQLite（零改造，850+ 测试不动）
- **云端**：新增 MySQL 适配层，Demo 真实读写 RDS

这样既满足赛题，又不必承担「六张表全量迁移 + FTS5 → ngram + 全部测试回归」
的成本 —— 而那笔成本产出的只是"工程完整性"，不是评分权重更高的东西
（初赛是创新性 60% + 应用价值 40%，**纯材料评审**）。

## 三、RDS 表设计

云侧只有**四张**表，**逐列与 `vigil/store.py` 一致**（这样下游查询不用改）：

```sql
CREATE TABLE items (
  item_id BIGINT PRIMARY KEY, kind VARCHAR(64) NOT NULL, title TEXT NOT NULL,
  detail TEXT, event_ts BIGINT NOT NULL, deadline_ts BIGINT,
  group_id BIGINT NOT NULL, actor_uid VARCHAR(64), place TEXT, links TEXT,
  amount VARCHAR(255), confidence DOUBLE NOT NULL, model VARCHAR(191) NOT NULL,
  prompt_ver VARCHAR(64) NOT NULL, created_at BIGINT NOT NULL
) ENGINE=InnoDB;
-- 以及 item_sources / digests / digest_items
```

### 两处 MySQL 差异（已知工作项，不藏）

| 差异 | SQLite 做法 | MySQL 做法 |
|---|---|---|
| **部分索引** | `CREATE INDEX ... WHERE deadline_ts IS NOT NULL` | MySQL 不支持 ⇒ 建普通索引 |
| **全文检索** | FTS5 `tokenize='trigram'` | 演示用 `LIKE`（`store.py` 已有 `_escape_like` 这条退路）；生产路径是 `FULLTEXT ... WITH PARSER ngram`，**本轮不启用** |

## 四、适配层：方言垫片，**不新建 `store_mysql.py`**

```python
# vigil/db.py
def connect(config, *, readonly: bool, dialect=None)   # SQLite: mode=ro / MySQL: 只读账号
def open_overlay(conn, *, dialect)                     # ATTACH ov / USE ov
def q(sql, dialect)                                    # '?' → '%s'
def upsert(table, cols, dialect)                       # INSERT OR REPLACE / REPLACE INTO
```

**为什么不抄一份 store**：仓内自己写过这条教训 ——

> `SELECT deleted FROM item_state` 是**第二份实现**——它一定会漂移。

新建 `store_mysql.py` 等于把 1252 行查询逻辑抄第二遍，然后两份开始漂移。
垫片把方言差异收敛到四个函数。

**为什么这个垫片是可行的**（三条已验证的事实）：
1. overlay 查询已是 schema 限定（`ov.item_edits`）—— MySQL 的 `database`
   就等于 SQLite `ATTACH` 出来的 schema，语义天然对齐
2. FTS 退路**已经写好了**：`store.search_items` 本就有 `LIKE` 分支
3. 写点极少：`INSERT OR REPLACE` 仅两处、`OR IGNORE` 两处

### `mode=ro` 不变量在 MySQL 上怎么保持

SQLite 用 `file:...?mode=ro` 从**连接层**保证只读。MySQL 没有这个语法，
等价的机械保证是**只读账号** + `SET SESSION TRANSACTION READ ONLY`：

```sql
GRANT SELECT ON vigil.* TO 'vigil_ro'@'%';
```

「Web 侧绝不写主库」这条不变量因此**依然成立**，只是换了个机制。

## 五、DCS（Redis）用在哪

| 用途 | key / 机制 | TTL |
|---|---|---|
| 日报列表/详情缓存 | `vigil:digests:v{n}:...`（版本号自增失效） | 300s |
| 搜索结果缓存 | `vigil:search:{sha1(query)}` | 60s |
| **分布式写锁** | `SET NX PX` + Lua 释放（校验 token） | 30s |

**如实说明**：本次是**单 ECS 部署**，进程内锁与分布式锁**行为等价**。
引入 DCS 锁的价值是：
1. 满足赛题「关联开通 REDIS」这条硬要求
2. 让"水平扩容时锁语义不退化为无锁"这件事**有现成实现**

**讲清楚比假装需要强** —— 材料里照上面这么写。

## 六、Terraform 与前置

### `deploy/terraform/` 是**我们自己的** Terraform 根

**不做**「把 `rds.tf` 塞进 `.auto-deploy/terraform/`」—— 那是 Skill 的工作目录，
重跑会覆盖。**做**：从 Skill 的 `templates/terraform/ecs-web` **fork** 出我们自己的，
同时定义 ECS/EIP/SG/VPC + `rds.tf`/`dcs.tf`。

这样 `terraform destroy` 一次性清干净，**不会留下一台按小时计费的 RDS**。

### 为什么官方 Skill 不够

`auto-deploy` 的 `SKILL.md` 明写：

> **Out of scope:** `RDS/Redis/OBS/MQ/ELB/CCE/Kubernetes stacks`

但华为云 Terraform provider **原生支持** `huaweicloud_rds_instance` 与
`huaweicloud_dcs_instance`（**DCS 就是华为云的 Redis**），且 Skill 的
`.tfrc` 已配好 provider 镜像源。所以补缺口是**声明式工作**。

### 前置（卡在账号操作上）

```bash
# ① 华为云控制台创建 AK/SK，然后**只存环境变量**
export HW_ACCESS_KEY="..."
export HW_SECRET_KEY="..."

# ② 密码也走 TF_VAR_，**绝不写进 terraform.tfvars**
export TF_VAR_rds_password="$(openssl rand -base64 24)"
export TF_VAR_dcs_password="$(openssl rand -base64 24)"

# ③ Terraform ≥ 1.8.0
terraform -version
```

⚠️ **AK/SK 与密码绝不进 git、README、PPT 或截图**。
`deploy/terraform/*.tfstate` 含密码明文 ⇒ 已在 `.gitignore` 里挡住。

## 七、验收（硬性）

```bash
terraform validate && terraform fmt -check -recursive     # 全绿
terraform apply -auto-approve
curl -fsS http://$EIP:8000/api/items?limit=1               # 200 且非空
mysql -h $RDS -e "SELECT COUNT(*) FROM vigil.items"        # > 0
redis-cli -h $DCS PING                                      # PONG
# ⚠️ destroy 跑不通不许往下走
terraform destroy -auto-approve
```

**最后一条是硬闸**：ECS + EIP + RDS 按小时计费，
而"忘了 destroy"是这类项目最贵的低级错误。
